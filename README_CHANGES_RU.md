# ExtIO_Pluto — журнал изменений

Форк оригинального [ExtIO_Pluto](https://github.com/lesha108/ExtIO_Pluto/) с
добавленным GUI управления приёмником и переводом сборки с Visual Studio на
CMake + VS Code. Ниже — полный список изменений, сделанных к текущему
моменту, в порядке их появления.

Изменённые/добавленные файлы:
- `ExtIO_Pluto.cpp` — вся логика
- `ExtIO_PlutoSDR.rc` — диалог GUI
- `resource.h` — ID контролов диалога
- `CMakeLists.txt` — сборка через CMake (новый файл, заменяет `.sln`/`.vcxproj`)
- `.vscode/settings.json` — настройки CMake Tools для VS Code (новый файл)

---

## 1. Новые органы управления в GUI

Диалог ExtIO увеличен со 168×33 до 230×143 и теперь содержит:

| Контрол | Что делает |
|---|---|
| **PlutoSDR URI** + кнопка Connect | было и раньше — `usb:1.2.5` или `ip:192.168.x.x` |
| **Sample rate** (выпадающий список) | 10 пресетов от 528 кГц до 20 МГц, отсортированы по возрастанию |
| **Gain mode** (выпадающий список) | Manual / Slow AGC / Fast AGC / Hybrid AGC (атрибут AD9361 `gain_control_mode`) |
| **RX Gain, dB** (поле ввода) | активно только в режиме Manual; атрибут `hardwaregain` |
| **RX filter BW, Hz** (поле ввода) | атрибут `rf_bandwidth`; пока не тронуто вручную — авто = 0.8×sample rate |
| **BW step** (выпадающий список) | шаг колеса мыши для поля BW: 1/10/100 кГц, 1/10 МГц |

Список sample rate генерируется в GUI динамически из `ExtIoGetSrates()` —
добавлять новые пресеты можно, просто дописав значения в массив
`kPresetSrates[]` внутри этой функции.

## 2. Управление колесом мыши

Поля **RX Gain** и **RX filter BW** подписаны на `WM_MOUSEWHEEL` через
классический Win32 subclassing (`SetWindowLongPtr(..., GWLP_WNDPROC, ...)`):
клик в поле (фокус) → прокрутка колеса меняет значение на шаг (1 дБ для
Gain, выбранный в комбобоксе BW step — для BW) и сразу применяет его к
железу.

## 3. Применение "на лету" без кнопок Apply

- **Gain и BW** — применяются по мере набора текста (`EN_CHANGE`), кнопки
  Apply убраны, поля растянуты на освободившееся место.
- **Sample rate** — сознательно **оставлен только выбор из выпадающего
  списка**. Ручной ввод произвольного значения пробовали добавить (через
  редактируемый комбобокс + кнопку Set), но отказались от этой идеи — при
  вводе многозначных чисел с высоким минимальным порогом (520 833 Гц)
  промежуточные значения то и дело обрезались по нижней границе и
  затирали то, что печаталось. Решили не усложнять и вернуться к простому
  списку пресетов.

## 4. Сборка через CMake + VS Code вместо Visual Studio

Добавлен `CMakeLists.txt` — теперь не нужен ни `.sln`/`.vcxproj`, ни именно
древний тулсет v140/v140_xp из оригинального проекта: подходит любой
современный MSVC (из "Build Tools for Visual Studio", без установки полной
IDE).

Важные детали `CMakeLists.txt`:
- `libiio.lib` и все runtime-DLL в репозитории — **32-битные (x86)**, сборка
  жёстко проверяет `CMAKE_SIZEOF_VOID_P == 4` и падает с понятной ошибкой,
  если выбран kit `amd64`/`x64` вместо `x86`.
- Экспорт функций (`InitHW`, `StartHW`, ...) по-прежнему берётся из
  `ExtIO_Pluto.def`, просто путь к нему передаётся через `/DEF:` в линкере
  вместо поля в свойствах проекта VS.
- `.rc`-файл компилируется автоматически (CMake сам находит `rc.exe` для
  MSVC-тулчейна).

Пошаговая инструкция по установке Build Tools, выбору kit'а (обязательно
**x86**, не amd64!) и сборке — см. `README_VSCODE_BUILD.md` (если нужен,
могу пересобрать/актуализировать отдельным файлом).

## 5. Сохранение всех настроек между запусками HDSDR

### Почему не через встроенный механизм HDSDR

Изначально пробовали штатный API `ExtIoGetSetting`/`ExtIoSetSetting` — он
оказался ненадёжным: HDSDR не всегда корректно восстанавливал новые (не
предусмотренные исходным автором) поля, из-за чего Gain и BW иногда
сбрасывались на дефолт при перезапуске.

### Попытка №1 — реестр Windows (отклонена)

Затем сделали сохранение в `HKEY_CURRENT_USER\Software\R2AJP\ExtIO_Pluto`
через Advapi32 (`RegOpenKeyEx`/`RegSetValueEx`...), вызывая загрузку из
`DllMain`. Тоже не заработало надёжно — вероятная причина: вызов функций
`Advapi32.dll` прямо из `DllMain` рискует попасть в классическую ловушку
loader lock (если `Advapi32.dll` ещё не была подгружена в процесс на тот
момент). От реестра отказались в пользу простого файла.

### Финальное решение — файл `ExtIO_Pluto_settings.ini` рядом с DLL

Простой текстовый файл `ключ=значение`, путь к которому вычисляется через
`GetModuleFileNameA` от собственного `__ImageBase` — то есть файл всегда
лежит в той же папке, куда скопирован сам `ExtIO_Pluto.dll`.

Что сохраняется:

```
GainModeIdx=0
GainDB=49.00
BWHz=3000000
BWAuto=0
BWStepIdx=1
SampleRateIdx=4
SDR=ip:192.168.3.1
DialogX=812
DialogY=430
```

Когда сохраняется:
- при любом изменении Gain/BW (набор текста, колесо мыши);
- при смене Gain mode / BW step / Sample rate;
- при успешном Connect;
- при перемещении окна диалога (после отпускания мыши, `WM_EXITSIZEMOVE`);
- при закрытии HDSDR (`CloseHW`) — финальный "предохранитель".

Когда загружается:
- в начале `InitHW()`, **после** создания debug-консоли (важно для
  диагностики через `_MYDEBUG`) и **до** подключения к железу через `gSDR`;
  защищено флагом `!gbInitHW`, чтобы не перечитывать файл повторно, если
  хост вызовет `InitHW` больше одного раза за сессию.

### Два найденных и исправленных бага восстановления

1. **`ExtIoSetSetting` перезаписывал восстановленные значения.** HDSDR
   вызывает этот метод сам, до `InitHW`, и если в его *собственном* `.ini`
   для этих полей ничего не сохранено — передаёт пустые/нулевые значения,
   которые затирали то, что мы только что подняли из своего файла.
   **Исправление:** `ExtIoSetSetting` теперь ничего не делает с нашими
   полями (оставлена только формальная обработка идентификатора `idx==0`).

2. **Фантомный `EN_CHANGE` от создания контролов.** Поля `IDC_EDIT_GAIN` /
   `IDC_EDIT_BW` в `.rc`-шаблоне имеют текст-заглушку `"0"` и `"2000000"`.
   Создание Edit-контрола с таким текстом само по себе генерирует
   `WM_SETTEXT` → `EN_CHANGE`, а наш обработчик "живого" применения
   воспринимал это как настоящий пользовательский ввод и тут же сохранял
   заглушку в файл, затирая только что загруженные значения.
   **Исправление:** флаг `gDialogReady` — `EN_CHANGE` игнорируется, пока
   диалог полностью не инициализирован (`UpdateDialog()` не отработал в
   конце `WM_INITDIALOG`).

## 6. Позиционирование окна

- **Центрирование при первом запуске.** Раньше диалог всегда создавался в
  координатах (0,0) — верхний левый угол экрана. Теперь при отсутствии
  сохранённой позиции окно центрируется на рабочей области экрана (через
  `SystemParametersInfoA(SPI_GETWORKAREA, ...)`, с учётом панели задач).
- **Запоминание позиции.** Координаты (`DialogX`/`DialogY`) сохраняются в
  `.ini` при перетаскивании окна и восстанавливаются при следующем запуске
  (с проверкой, что окно не окажется за пределами экрана, если разрешение
  изменилось).
- **Always-on-top.** Диалог создаётся с `HWND_TOPMOST` — остаётся поверх
  окна HDSDR (и вообще поверх всех окон) независимо от фокуса.

## Технические детали для дальнейшей разработки

- **Диапазоны:** Gain −10…77 дБ, BW 200 кГц…56 МГц — консервативные оценки
  под AD9361/AD9364; для конкретной ревизии Pluto стоит свериться с
  `iio_info -a` и при необходимости скорректировать константы в коде.
- **`_MYDEBUG`** активируется автоматически в Debug-сборке (завязано на
  `_DEBUG`) — открывает отдельную консоль с логами (`AllocConsole` внутри
  `InitHW`), туда же теперь пишет диагностика загрузки/сохранения `.ini`.
- **Обратная совместимость sample rate индексов:** список пресетов
  несколько раз пересортировывался в процессе разработки — при обновлении
  DLL старое содержимое `SampleRateIdx=` в `.ini` может временно указывать
  не на то значение, что раньше; достаточно один раз переустановить нужный
  Sample Rate из списка после обновления.
